01The starting position

Ubuntu 26.04 LTS ships strongSwan 6.0.4. The code supports ML-KEM, but nothing is quantum-safe until you write a proposal string on both peers.

This is the opposite of the SSH position. With OpenSSH the work is verifying an inherited default and stopping it from regressing. With strongSwan the work is deliberate configuration, applied symmetrically to both ends of every tunnel, because a proposal only takes effect where both peers agree on it.

Three pieces make the hybrid exchange possible. RFC 9242 adds the IKE_INTERMEDIATE exchange, which carries payloads too large for the initial exchange. RFC 9370 allows up to seven additional key exchanges beyond the first. FIPS 203 defines ML-KEM itself. strongSwan 6.0 implements all three.

1.1 What is and is not quantum-safe

StageTypical configurationStatus
IKE key exchange, defaultecp384 or x25519 aloneClassical only
IKE key exchange, configuredx25519-ke1_mlkem768Hybrid, quantum-safe
Child SA key exchange (PFS)ecp384-ke1_mlkem768Hybrid, quantum-safe
Peer authenticationECDSA, RSA, EAP, PSKClassical only
ESP bulk encryptionAES-GCM-256Quantum-safe

Hybrid key exchange defeats harvest-now-decrypt-later. Traffic recorded today cannot be decrypted later by an adversary who acquires a cryptanalytically relevant quantum computer.

Boundary of the control

This does not defend against an adversary who already holds such a machine and forges a certificate signature to impersonate a gateway in real time. That gap closes when ML-DSA certificates and IKEv2 authentication profiles are available end to end. Be precise about this when reporting upward, because "our VPN is quantum-safe" overstates what is in place.

1.2 How the exchange actually runs

The classical exchange happens first, in IKE_SA_INIT, exactly as before. The ML-KEM public key and ciphertext then travel in a separate IKE_INTERMEDIATE round trip, before IKE_AUTH. Both shared secrets feed the final key material. If either primitive fails, the other still holds.

Two consequences follow. The handshake gains one round trip. And the ML-KEM-768 public key is 1184 bytes, which pushes the message past the 1280-byte size every IKEv2 implementation must handle without IP fragmentation, so IKE-layer fragmentation becomes mandatory rather than optional.

Why the hybrid is structural

ML-KEM cannot be the initial IKE key exchange. A key encapsulation mechanism needs a request and a response to complete, which the initial exchange does not provide in the required form. An initial classical exchange is always necessary. Hybrid is therefore how IKEv2 works, not a transitional compromise you can later drop.

1.4 A note on version numbers

Upstream strongSwan has moved past 6.0.4. Canonical backports security fixes into the packaged version rather than tracking upstream point releases, which is normal for an LTS. Do not chase the upstream number. Track the Ubuntu package version and confirm the machine is current.

apt policy strongswan-swanctl libstrongswan

02Verify the baseline

Four checks establish whether a host can do post-quantum key exchange at all.

2.1 Install the right packages

Use the swanctl and vici configuration backend, not the legacy ipsec.conf starter. The legacy backend is still packaged, and installing the strongswan metapackage pulls it in. Only one of the two daemons should be present.

sudo apt install -y strongswan-swanctl charon-systemd strongswan-pki
sudo apt remove -y strongswan-starter strongswan-charon

Confirm which daemon is active. Two units running at once is a common cause of configuration that appears to load but never takes effect.

systemctl list-units 'strongswan*' --all --no-pager

2.2 Version

swanctl --version

Expect something close to the following. The Ubuntu suffix will differ as security updates land. The 6.0.4 part is what matters, and anything below 6.0.0 cannot do ML-KEM at all.

strongSwan 6.0.4

2.3 Confirm ML-KEM is loaded

This is the check that decides whether the rest of the guide applies. It lists the algorithms the running daemon actually has, and the plugin providing each one.

sudo swanctl --list-algs | grep -i ml_kem
ML_KEM_512[ml]
ML_KEM_768[ml]
ML_KEM_1024[ml]

The name in brackets is the implementing plugin. It may read [openssl] instead of [ml], which is equally valid. Ubuntu 26.04 ships OpenSSL 3.5, and the openssl plugin provides ML-KEM from that version onward. What matters is that the three names appear.

2.4 If nothing is returned

Work through these in order.

  1. Check which plugins loaded: sudo swanctl --stats prints the full list.
  2. Check the OpenSSL version: openssl version. Below 3.5, the openssl plugin cannot supply ML-KEM.
  3. Install the extra plugin set: sudo apt install -y libstrongswan-extra-plugins.
  4. Check for a plugin disabled in configuration: grep -r load /etc/strongswan.d/charon/ml.conf.
  5. Restart the daemon after any change, then repeat the check in 2.3.

03Configure the gateway

Post-quantum key exchange in strongSwan is one proposal string. Everything else in this section exists to make that string take effect and stay in place.

3.1 Choose a posture

Strict, hybrid required

Any peer that cannot do RFC 9370 additional key exchanges is refused. Aim for this on gateway-to-gateway tunnels, where you control both ends and the peer list is short and known.

proposals = aes256gcm16-prfsha384-ecp384-ke1_mlkem1024

That string is the CNSA 2.0 profile: AES-256 in GCM, SHA-384 as the pseudo-random function, an initial P-384 exchange and ML-KEM-1024 in the first additional round. For a general enterprise tunnel, ML-KEM-768 with X25519 is the more common pairing and carries a smaller payload.

proposals = aes256gcm16-prfsha256-x25519-ke1_mlkem768

Preferred, with classical fallback

Hybrid when both ends support it, classical when they do not. Appropriate for concentrators serving a mixed peer estate during transition. Separate proposals with a comma. Order sets preference, and strongSwan prefers its own configured order by default when acting as responder.

proposals = aes256gcm16-prfsha384-ecp384-ke1_mlkem768, aes256gcm16-prfsha384-ecp384
The fallback is silent

A peer that drops to the second proposal produces no warning and no error. The tunnel comes up and looks healthy. Only test 1 in section 5 tells you which proposal was actually selected, which is why that test has to be per tunnel and repeated after every peer change.

Sequencing

Do not go strict before completing the inventory in section 6. Cloud VPN endpoints, hardware concentrators and native operating system clients are the usual casualties.

3.2 Write the connection file

The packaged /etc/swanctl/swanctl.conf includes conf.d/*.conf. Use a drop-in there rather than editing the main file, so package upgrades do not conflict with your change. Confirm the include line is present first.

grep -n 'include' /etc/swanctl/swanctl.conf

A gateway-to-gateway tunnel with certificate authentication and hybrid key exchange on both the IKE SA and the Child SA:

sudo tee /etc/swanctl/conf.d/60-pqc.conf > /dev/null <<'EOF'
# Hybrid post-quantum IKEv2. X25519 + ML-KEM-768.
# Owner: <team>   Reviewed: 2026-08-03
connections {
    dc-a-to-dc-b {
        version = 2
        local_addrs  = 203.0.113.10
        remote_addrs = 198.51.100.20

        proposals = aes256gcm16-prfsha384-x25519-ke1_mlkem768
        fragmentation = yes
        dpd_delay = 30s

        local {
            auth  = pubkey
            certs = gw-dc-a.pem
            id    = gw-dc-a.example.gov.sg
        }
        remote {
            auth = pubkey
            id   = gw-dc-b.example.gov.sg
        }

        children {
            net-to-net {
                local_ts  = 10.10.0.0/16
                remote_ts = 10.20.0.0/16
                esp_proposals = aes256gcm16-x25519-ke1_mlkem768
                start_action  = trap
            }
        }
    }
}
EOF

sudo chmod 600 /etc/swanctl/conf.d/60-pqc.conf

3.3 Fragmentation is not optional

The ML-KEM payload will not fit in a single IKE message. Without IKE-layer fragmentation the exchange relies on IP fragmentation, which middleboxes and firewalls drop far more often. Set it explicitly rather than trusting the default, so the requirement is visible in the file to whoever reads it next.

If handshakes stall after IKE_SA_INIT succeeds, fragmentation is the first thing to check, followed by any firewall rule that treats UDP 4500 differently from UDP 500.

3.4 Perfect forward secrecy on the Child SA

The key exchange transform is mandatory for the IKE SA and optional for the Child SA. Omitting it means Child SA keys are derived from IKE SA material, so the post-quantum protection is inherited but not refreshed. Including ke1_mlkem768 in esp_proposals, as above, gives each Child SA and each rekey its own hybrid exchange.

Since 6.0.2 the default ESP proposals include the supported key exchange methods along with none, which makes the exchange optional. Configure the proposal explicitly if you want it guaranteed.

3.5 Load and validate

Loading parses the file and reports errors. It does not restart anything, so it is safe to run on a live gateway.

sudo swanctl --load-all
sudo swanctl --list-conns

Confirm the proposal printed back to you is exactly the one you wrote. A typo in an algorithm keyword is rejected outright, but a valid keyword in the wrong slot is accepted and quietly changes the security you get.

Keep a way back in

If you administer the gateway over the tunnel you are changing, open a second path first, out of band or over the management network. Confirm the new configuration works before closing it.

3.6 Raise logging while you test

sudo tee /etc/strongswan.d/charon-logging.conf > /dev/null <<'EOF'
charon-systemd {
    journal {
        default = 1
        ike = 2
        cfg = 2
    }
}
EOF

sudo systemctl restart strongswan
journalctl -u strongswan -f

Lower these values again once testing is complete. Level 2 on a busy concentrator produces a great deal of output.

04Configure the remote peer

A proposal is a negotiation, not a setting. Configuring one end achieves nothing on its own.

On a second Ubuntu 26.04 gateway, mirror the file: swap local_addrs with remote_addrs, swap local_ts with remote_ts, swap the identities and certificates, and keep the proposal strings byte-identical. Mismatched proposals are the most common cause of a tunnel that will not establish after this change.

Where the peer is not strongSwan, the requirement is that it supports RFC 9370 additional key exchanges and RFC 9242 intermediate exchange, and that its own configuration names ML-KEM in the same round. Vendor syntax differs, and support varies widely by platform and software version. Confirm it from the vendor's documentation before assuming a tunnel will come up.

Native operating system clients

The IKEv2 clients built into Windows, iOS and macOS do not negotiate RFC 9370 additional key exchanges. Remote access users on those clients will fail against a strict posture. The strongSwan Android client can do it, but only with the proposal configured explicitly in the profile. Treat remote access and gateway-to-gateway as separate migrations with separate timelines.

05Testing

Six tests in increasing order of rigour. Run at least tests 1, 2 and 3.

Test 1What was actually negotiated

The single most important check. Bring the tunnel up, then read the established SA.

sudo swanctl --initiate --child net-to-net
sudo swanctl --list-sas

The line that matters names the exchange in each round:

AES_GCM_16-256/PRF_HMAC_SHA2_384/CURVE_25519/KE1_ML_KEM_768

CURVE_25519 is the initial exchange. KE1_ML_KEM_768 is the additional exchange in round one. If the KE1_ element is absent, the tunnel is classical, whatever the configuration file says.

Test 2Every proposal on the box

Test 1 tells you what one tunnel negotiated. This tells you what the gateway is configured to offer across all of them, and it catches the case a single tunnel test misses: a second drop-in file, written for another connection, carrying a classical proposal.

sudo swanctl --load-all
grep -Hn 'proposals' /etc/swanctl/swanctl.conf /etc/swanctl/conf.d/*.conf

The first command names every connection it loaded, so a file that failed to parse or was never picked up is visible immediately. The second lists every proposal line with its file and line number.

Under a strict posture, every line returned should contain a ke1_ element. Any that does not is a tunnel with no post-quantum protection, whatever the rest of the estate looks like.

Test 3Negative test

A positive test alone is weak evidence. It proves the preferred path works, not that the classical path is closed. On the initiating gateway only, strip the post-quantum element from the proposal and confirm the responder refuses the connection. Take a copy first.

sudo cp /etc/swanctl/conf.d/60-pqc.conf /tmp/60-pqc.conf.bak
sudo sed -i 's/-ke1_mlkem[0-9]*//g' /etc/swanctl/conf.d/60-pqc.conf
sudo swanctl --load-all
sudo swanctl --initiate --child net-to-net

Under strict enforcement on the responder, expect the exchange to fail:

received NO_PROPOSAL_CHOSEN notify error
establishing IKE_SA failed, peer not responding

Restore the file and reload before doing anything else.

sudo cp /tmp/60-pqc.conf.bak /etc/swanctl/conf.d/60-pqc.conf
sudo swanctl --load-all
sudo swanctl --list-sas

A tunnel that comes up during the test means the responder still accepts classical key exchange. This is the test that catches a drop-in written but never loaded, and a responder still carrying a fallback proposal someone forgot to remove.

Test 4Pin each parameter set individually

Verify each parameter set you intend to accept, rather than trusting negotiation to select the one you expect. Run this only if the responder is configured to accept more than one.

sudo cp /etc/swanctl/conf.d/60-pqc.conf /tmp/60-pqc.conf.bak

for k in mlkem768 mlkem1024; do
  printf '%-11s ' "$k"
  sudo sed -i "s/ke1_mlkem[0-9]*/ke1_$k/g" /etc/swanctl/conf.d/60-pqc.conf
  sudo swanctl --load-all >/dev/null 2>&1
  sudo swanctl --initiate --child net-to-net >/dev/null 2>&1 && echo OK || echo FAIL
  sudo swanctl --terminate --ike dc-a-to-dc-b >/dev/null 2>&1
done

sudo cp /tmp/60-pqc.conf.bak /etc/swanctl/conf.d/60-pqc.conf
sudo swanctl --load-all

A FAIL here is not necessarily a fault. It usually means the responder does not offer that parameter set, which is worth knowing before someone changes the initiator and cannot explain why the tunnel stopped.

Test 5Prove it on the wire

Independent of anything strongSwan reports about itself. Capture the handshake and look for the intermediate exchange.

sudo tcpdump -i any --immediate-mode -U -n 'port 500 or port 4500' -w /tmp/pqc.pcap &
TCPDUMP_PID=$!
sleep 1
sudo swanctl --initiate --child net-to-net
sleep 1
sudo kill $TCPDUMP_PID
tcpdump -r /tmp/pqc.pcap -n -vv 2>/dev/null | grep -E 'parent_sa|child_sa'

A classical handshake goes straight from the initial exchange to authentication. A hybrid handshake has an extra exchange wedged between them, shown as #43 because tcpdump has no name for exchange type 43. Seeing #43 is the proof that the post-quantum round trip happened.

parent_sa ikev2_init[I]
parent_sa ikev2_init[R]
child_sa  #43[I]        <- ML-KEM public key, fragment 1
child_sa  #43[I]        <- fragment 2
child_sa  #43[R]        <- ML-KEM ciphertext
child_sa  ikev2_auth[I]
child_sa  ikev2_auth[R]

The two fragments in the request are the expected behaviour, not a fault. They are the 1184-byte ML-KEM public key crossing the 1280-byte message ceiling once headers are added.

Test 6Measure the cost

Bring numbers when someone asks about performance impact.

for i in $(seq 1 20); do
  sudo swanctl --terminate --ike dc-a-to-dc-b >/dev/null 2>&1
  ( time sudo swanctl --initiate --child net-to-net >/dev/null 2>&1 ) 2>&1 | grep real
done

Run it once with the hybrid proposal and once with the classical proposal, then compare. Published measurements on a local network put the difference at roughly one millisecond, almost all of it the extra round trip rather than the arithmetic. The authentication exchange is unchanged in size. The whole cost of the hybrid sits in that one added round trip, about two kilobytes.

Sequencing note. This test needs the classical proposal still available for comparison. Run it before applying the strict posture, or against a staging pair.

06Compatibility checklist

Test each of these against a candidate gateway before requiring hybrid key exchange. This is where rollouts fail.

  • Peer gateways running strongSwan below 6.0.0, which cannot do ML-KEM at any version of the configuration
  • Hardware VPN concentrators and firewalls terminating IPsec, each on its own software timeline
  • Cloud provider VPN gateways, where the proposal set is fixed by the provider and not by you
  • Remote access users on native Windows, iOS and macOS clients
  • Firewalls and middleboxes that drop fragmented IKE, or that treat UDP 4500 differently from UDP 500
  • Path MTU on the tunnel path, particularly over links with tunnelling already in place
  • Any peer behind NAT, where fragmented exchanges are more fragile
  • Monitoring and alerting that parses tunnel status output, since the proposal string it reads will change shape
  • High availability pairs, which must be upgraded together or will fail over into a classical configuration

For anything that fails, upgrade it. If that is not possible, carve out a narrow exception with a separate connection definition and a permissive proposal, rather than weakening the proposal on the connections that already work.

An interim option for old peers

RFC 8784 post-quantum preshared keys mix an out-of-band secret into the key derivation, giving quantum resistance without any post-quantum algorithm on the wire. strongSwan has supported this since 5.7.0, via ppk_id on the connection and a ppk section in secrets. It suits peers that cannot be upgraded, at the cost of distributing and rotating a shared secret. It is a different control with a different key management burden, so scope it as its own piece of work.

Record every exception with an owner and a review date. An exception without a review date becomes permanent.

07Evidence to record

Capture the following per gateway pair for an audit or assurance file.

  1. swanctl --version and apt policy strongswan-swanctl output
  2. sudo swanctl --list-algs | grep -i ml_kem output, showing the algorithm is available
  3. Test 1 output, showing the negotiated proposal including the KE1_ML_KEM element
  4. Test 3 output, showing that classical key exchange is refused
  5. Test 5 capture, or the filtered line list, showing the intermediate exchange
  6. The connection file itself, with its owner and review date
  7. Date of the check and the name of the person who ran it
Why items 3 and 4 matter

Together they are what distinguish a verified control from a configured one. Configuration evidence alone proves intent. Only the negative test proves the classical path is actually closed, and on a negotiated protocol that is the difference that counts.

08What this does not cover

Be precise about the boundary when reporting this work upward.

  • Authentication remains classical. Gateway and user authentication still rests on ECDSA or RSA certificates, or on preshared keys and EAP. ML-DSA certificates are not part of this configuration. Plan a rotation for when post-quantum certificate support is available across your PKI, your gateways and your peers.
  • IKEv1 is out of scope entirely. It has no equivalent mechanism. Tunnels still running IKEv1 need migrating to IKEv2 before any of this applies.
  • The ESP data plane was already fine. AES-GCM with a 256-bit key is quantum-safe with adequate key length. Nothing here changes it, and nothing needed to.
  • Both ends, every time. A hybrid-capable gateway reached by a classical peer negotiates classical key exchange, and the traffic is not protected against harvest-now-decrypt-later. Peer estate coverage is the harder half of the problem, and section 6 is where it starts.
  • Other services need separate assessment. TLS, SSH, certificate issuance and application-layer cryptography each have their own migration path and their own timelines.
