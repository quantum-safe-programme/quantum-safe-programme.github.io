01The starting position

Ubuntu 26.04 LTS ships OpenSSH 10.2p1 with hybrid post-quantum key exchange active by default. There is no toggle to enable and no package to install.

The default first-preference key exchange is mlkem768x25519-sha256. It combines ML-KEM-768, the lattice-based KEM standardised by NIST in FIPS 203, with classical X25519 elliptic-curve Diffie-Hellman. Both halves run and their secrets are combined. If the post-quantum half is later found to be flawed, the classical half still holds. If the classical half falls to a quantum computer, the post-quantum half holds.

This changes what your work looks like. You are not enabling a feature. You are verifying an inherited default, enforcing it so it cannot silently regress, and proving the enforcement holds.

1.1 What is and is not quantum-safe

Handshake stageAlgorithm on 26.04Status
Key exchangemlkem768x25519-sha256Hybrid, quantum-safe
Host key (server auth)Ed25519, ECDSA, RSAClassical only
User auth (public key)Ed25519, ECDSA, RSA, FIDO2Classical only
Bulk encryptionChaCha20-Poly1305, AES-GCMQuantum-safe

Hybrid key exchange defeats harvest-now-decrypt-later. Traffic recorded today cannot be decrypted later by an adversary who acquires a cryptanalytically relevant quantum computer.

Boundary of the control

This does not defend against an adversary who already holds such a machine and attacks the Ed25519 host key in real time to impersonate the server. That gap closes when ML-DSA host keys ship. OpenSSH has not released them. Be precise about this when reporting upward, because "SSH is quantum-safe" overstates what is in place.

1.2 Algorithm names you will see

Three names appear in 26.04. All three are quantum-safe.

mlkem768x25519-sha256
ML-KEM-768 with X25519
The default and the one to prefer. NIST-standardised under FIPS 203, and the name that procurement language and audit checklists increasingly cite.
First preference
sntrup761x25519-sha512
Streamlined NTRU Prime with X25519
Standardised as RFC 9941. Retained as fallback, and the algorithm OpenSSH shipped by default before ML-KEM arrived.
Fallback
sntrup761x25519-sha512@openssh.com
Vendor name for the same construction
Kept for clients that predate the standardised name. Dropping it locks out OpenSSH 9.x clients for no security gain.
Compatibility

1.3 A note on version numbers

Upstream OpenSSH has moved past 10.2. Canonical backports security fixes into the 10.2p1 package rather than tracking upstream point releases, which is normal for an LTS. Do not chase the upstream version number. Track the Ubuntu package version and confirm the machine is current.

apt policy openssh-server

02Verify the baseline

Four commands establish where a host actually stands.

2.1 Version

ssh -V

Expect something close to the following. The Ubuntu suffix will differ as security updates land. The 10.2p1 part is what matters.

OpenSSH_10.2p1 Ubuntu-2ubuntu3.2, OpenSSL 3.5.5

2.2 Algorithms compiled into the binary

ssh -Q kex | grep -Ei 'mlkem|sntrup'

Expect all three names from section 1.2. This tells you what the binary can do, not what it is configured to do.

2.3 Effective server configuration

sudo sshd -T | grep -i '^kexalgorithms'

This resolves every include and drop-in and prints the list the daemon will actually offer. It is the authoritative answer. Do not rely on reading /etc/ssh/sshd_config by eye.

2.4 Negotiated algorithm on a live session

ssh -v user@server exit 2>&1 | grep -i 'kex: algorithm'
debug1: kex: algorithm: mlkem768x25519-sha256

If all four checks pass, the default is intact. Move to enforcement.

03Enforce on the server

The default is correct but unenforced. Anything that appends a permissive KexAlgorithms line can quietly reintroduce classical key exchange.

Hardening scripts written for an older release, configuration management templates and vendor agent installers are the usual culprits. An explicit policy file prevents regression and gives you something to point an auditor at.

3.1 Choose a posture

Strict, post-quantum only

Any client that cannot do hybrid key exchange is refused. Aim for this on high-value systems and on any estate where you control the client population.

KexAlgorithms mlkem768x25519-sha256,sntrup761x25519-sha512,sntrup761x25519-sha512@openssh.com

Preferred, with classical fallback

Quantum-safe when both ends support it, but old clients and appliances still connect. Appropriate for shared bastions and mixed estates during transition.

KexAlgorithms mlkem768x25519-sha256,sntrup761x25519-sha512,sntrup761x25519-sha512@openssh.com,curve25519-sha256,curve25519-sha256@libssh.org
Sequencing

Do not go strict before completing the inventory in section 6. Backup agents, monitoring probes, network appliances and CI runners are the usual casualties.

3.2 Write a drop-in file

/etc/ssh/sshd_config includes /etc/ssh/sshd_config.d/*.conf at the top of the file. OpenSSH takes the first value it sees for most keywords, so a drop-in wins over anything later in the main file. Use a drop-in rather than editing sshd_config directly, so package upgrades do not conflict with your change.

sudo tee /etc/ssh/sshd_config.d/60-pqc.conf > /dev/null <<'EOF'
# Quantum-safe key exchange. Hybrid PQ/T only.
# Owner: <team>   Reviewed: 2026-08-01
KexAlgorithms mlkem768x25519-sha256,sntrup761x25519-sha512,sntrup761x25519-sha512@openssh.com
EOF

sudo chmod 644 /etc/ssh/sshd_config.d/60-pqc.conf

3.3 Validate before reloading

Never reload without testing the syntax. A broken sshd_config on a remote host is a site visit.

sudo sshd -t && echo "config OK"
sudo sshd -T | grep -i '^kexalgorithms'

Confirm the second command returns exactly the list you intended.

3.4 Reload safely

Keep your current session open

Open a second terminal to test. If the new configuration locks you out, the first session is your way back in. Close it only once the new session is confirmed working.

Ubuntu 26.04 uses socket activation, so both units need attention. Restarting only ssh.service leaves the socket unit holding the old configuration.

sudo systemctl restart ssh.socket ssh.service

Confirm the daemon is healthy and listening.

systemctl status ssh --no-pager
sudo ss -tlnp | grep :22

04Enforce on the client

Server enforcement protects the server. Client enforcement protects your administrators when they connect outward to systems you do not control.

Both are needed for a complete control. System-wide configuration:

sudo tee /etc/ssh/ssh_config.d/60-pqc.conf > /dev/null <<'EOF'
Host *
    KexAlgorithms mlkem768x25519-sha256,sntrup761x25519-sha512,sntrup761x25519-sha512@openssh.com
EOF

Per-user, in ~/.ssh/config, a softer form that raises post-quantum key exchange to first preference without breaking access to legacy kit:

Host *
    KexAlgorithms ^mlkem768x25519-sha256,sntrup761x25519-sha512

The ^ prefix prepends to the built-in default list rather than replacing it. On an administrator workstation this is usually the right choice.

4.1 Use the built-in warning as a discovery tool

The OpenSSH 10.2 client prints a warning whenever a session negotiates classical key exchange.

** WARNING: connection is not using a post-quantum key exchange algorithm.
** This session may be vulnerable to "store now, decrypt later" attacks.
** The server may need to be upgraded.

This is free estate discovery. Ask administrators to report every host that triggers it. That list becomes your remediation backlog, and it will surface systems no inventory captured.

05Testing

Six tests in increasing order of rigour. Run at least tests 1, 2 and 3.

Test 1Negotiated algorithm

The single most important check.

ssh -v user@server exit 2>&1 | grep -i 'kex: algorithm'
debug1: kex: algorithm: mlkem768x25519-sha256

Any curve25519-sha256 or diffie-hellman-* result means the connection is not quantum-safe.

Test 2The server's advertised proposal

Shows what the server offers, independent of what the client chose.

ssh -vv user@server exit 2>&1 | grep -A1 'peer server KEXINIT proposal' | grep 'KEX algorithms'

Every name in that list is one the server will accept. Under a strict posture, no classical name should appear.

Test 3Negative test

A positive test alone is weak evidence. It only proves the preferred path works, not that the fallback path is closed. Force a classical algorithm and confirm refusal.

ssh -o KexAlgorithms=curve25519-sha256 user@server exit

Under strict enforcement, expect:

Unable to negotiate with 10.0.0.5 port 22: no matching key exchange method found.
Their offer: mlkem768x25519-sha256,sntrup761x25519-sha512,sntrup761x25519-sha512@openssh.com

A successful login here means enforcement is not in place. This is the test that catches a drop-in file written but never loaded.

Test 4Pin each algorithm individually

Verify each accepted algorithm rather than trusting negotiation to pick the one you expect.

for k in mlkem768x25519-sha256 sntrup761x25519-sha512 sntrup761x25519-sha512@openssh.com; do
  printf '%-38s ' "$k"
  ssh -o KexAlgorithms="$k" -o BatchMode=yes -o ConnectTimeout=5 \
      user@server exit 2>/dev/null && echo OK || echo FAIL
done
Test 5External scan

Confirms the result from outside the host, using tooling that does not depend on your OpenSSH client configuration.

sudo apt install -y nmap
nmap -p 22 --script ssh2-enum-algos server

ssh-audit produces a more opinionated report, which is useful for an evidence pack.

sudo apt install -y ssh-audit
ssh-audit server
Test 6Measure the cost

Bring numbers when someone asks about performance impact.

for k in curve25519-sha256 mlkem768x25519-sha256; do
  printf '%-28s ' "$k"
  ( time ( for i in $(seq 1 20); do
      ssh -o KexAlgorithms="$k" -o BatchMode=yes user@server exit
    done ) ) 2>&1 | grep real
done

The hybrid handshake carries roughly 1.2 KB more data and adds a few milliseconds. On any real network this sits below the round-trip noise floor.

Sequencing note. This test needs the classical fallback still available for comparison. Run it before applying the strict posture, or against a staging host.

06Compatibility checklist

Test each of these against a candidate server before enforcing post-quantum only. This is where rollouts fail.

  • Backup and replication agents using SSH or SFTP transport
  • Configuration management and monitoring (Ansible, Salt, Zabbix, Nagios checks over SSH)
  • CI and CD runners, including hosted runners you do not control
  • Network appliances, out-of-band management and legacy switches
  • Embedded clients using Dropbear or libssh
  • Windows administrator workstations, including PuTTY, WinSCP and MobaXterm builds with embedded SSH libraries
  • Git remotes, if the server hosts repositories
  • Jump hosts and bastions in the connection path, which must also support the algorithm

For anything that fails, upgrade its SSH implementation. If that is not possible, carve out a narrow exception with a Match block rather than weakening the global policy.

Match Address 10.20.30.0/24
    KexAlgorithms +curve25519-sha256

Record every exception with an owner and a review date. An exception without a review date becomes permanent.

07Evidence to record

Capture the following per host for an audit or assurance file.

  1. ssh -V output, showing OpenSSH and OpenSSL versions
  2. sudo sshd -T | grep -i '^kexalgorithms' output, showing effective configuration
  3. Test 1 output, showing the negotiated algorithm
  4. Test 3 output, showing that classical key exchange is refused
  5. Date of the check and the name of the person who ran it
Why items 3 and 4 matter

Together they are what distinguish a verified control from a configured one. Configuration evidence alone proves intent. Only the negative test proves the fallback path is actually closed.

08What this does not cover

Be precise about the boundary when reporting this work upward.

  • Server and user authentication remain classical. ML-DSA host keys and user keys are not in OpenSSH 10.2. Keep Ed25519 host keys and plan a rotation for when post-quantum signature support ships.
  • SSH certificates are unchanged. Certificates signed by your CA still carry classical signatures.
  • Other services need separate assessment. TLS, IPsec, VPN concentrators and application-layer cryptography each have their own migration path.
  • The 26.04 default helps only where both ends are current. A 26.04 server reached by an OpenSSH 8.x client negotiates classical key exchange and the session is not protected. Client estate coverage is the harder half of the problem, and section 4.1 is the cheapest way to start mapping it.
