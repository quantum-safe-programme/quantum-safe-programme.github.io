01The starting position

Ubuntu 26.04 LTS ships nginx 1.28.x linked against OpenSSL 3.5.x, which negotiates hybrid post-quantum key exchange by default. There is no module to compile and no provider to install.

The default first-preference group is X25519MLKEM768. It combines ML-KEM-768, the lattice-based KEM standardised by NIST in FIPS 203, with classical X25519 elliptic-curve Diffie-Hellman. Both halves run and their secrets are combined. If the post-quantum half is later found to be flawed, the classical half still holds. If the classical half falls to a quantum computer, the post-quantum half holds.

This changes what the work looks like. Nobody is enabling a feature. The task is verifying an inherited default, pinning it so it cannot silently regress, and proving the pin holds. This is the same posture as OpenSSH on this release, with one difference worth holding onto throughout: SSH connects a known administrator to a known host, so refusing classical clients outright is a reasonable posture. NGINX usually serves the public internet, where the classical fallback is what keeps ordinary visitors connecting. The goal here is maximising PQC coverage, not enforcing it, except in the closed environments described in Section 3.1.

02Verify the baseline

Four checks establish where a host actually stands.

2.1 Version

nginx -V 2>&1 | grep -i openssl

Expect something close to:

nginx version: nginx/1.28.3 (Ubuntu)
built with OpenSSL 3.5.5 27 Jan 2026

Both the build-time and run-time OpenSSL versions must read 3.5 or higher. An older figure means a third-party build, a PPA, an F5 package, or a Docker image on an older base, which will not recognise hybrid group names.

2.2 Algorithms compiled into the library

openssl list -kem-algorithms | grep -i -E 'ml-?kem'
openssl list -signature-algorithms | grep -i -E 'ml-dsa|slh-dsa'

Expect ML-KEM-512/768/1024 plus the hybrid groups X25519MLKEM768, X448MLKEM1024, SecP256r1MLKEM768 and SecP384r1MLKEM1024, each marked @ default. That marker confirms the built-in provider, not a third-party module such as oqs-provider.

2.3 Effective server configuration

sudo nginx -T 2>/dev/null | grep -i 'ssl_ecdh_curve\|ssl_conf_command Groups'

This resolves every include and prints what the running configuration actually sets. An empty result is not an error. It means nginx is relying on the OpenSSL 3.5 built-in list, which already prefers the hybrid.

2.4 Negotiated group on a live handshake

openssl s_client -connect host:443 -tls1_3 /dev/null \
  | grep 'Negotiated TLS1.3 group'

Expect:

Negotiated TLS1.3 group: X25519MLKEM768

If the four checks above all pass, the default is intact. Move to pinning it.

03Pin the key exchange list

The default is correct but unpinned. A hardening template copied from an older baseline, a WAF vendor's recommended snippet, or a configuration management module written before OpenSSL 3.5, can append a classical-only ssl_ecdh_curve line and quietly disable PQC. An explicit policy file prevents that and gives an auditor something concrete to check.

3.1 Choose a posture

Preferred, with classical fallback. Quantum-safe when the client supports it, but older browsers, API clients and health-check tools still connect. This is the correct posture for anything public-facing.

ssl_conf_command Groups X25519MLKEM768:SecP256r1MLKEM768:X25519:secp256r1;

Strict, PQC only. Refuses any client that cannot do hybrid key exchange. Only appropriate for closed environments where every client is known and current: internal service-to-service mTLS, an admin API reachable only from a fixed fleet, a service mesh sidecar.

ssl_conf_command Groups X25519MLKEM768:SecP256r1MLKEM768;
Do not go strict on anything public

Unlike an SSH estate, you rarely control every client reaching a public nginx listener. A strict posture there turns away real visitors on older browsers and locks out monitoring and scanning tools that have not yet updated. Complete the checklist in Section 6 before considering it anywhere.

3.2 Write a drop-in file

Ubuntu's nginx.conf includes /etc/nginx/conf.d/*.conf from the http block. Use a drop-in rather than editing a server block directly, so a package upgrade or a template refresh does not silently overwrite the setting.

sudo tee /etc/nginx/conf.d/00-pqc.conf > /dev/null <<'EOF'
# Quantum-safe key exchange. Hybrid PQ/T preferred, classical fallback.
# Owner:    Reviewed: 2026-08-02
ssl_conf_command Groups X25519MLKEM768:SecP256r1MLKEM768:X25519:secp256r1;
EOF

sudo chmod 644 /etc/nginx/conf.d/00-pqc.conf

ssl_conf_command Groups is used in preference to ssl_ecdh_curve here. The ?-prefixed optional syntax and the newer tuple names are only reliably parsed through ssl_conf_command, and it applies at the http level cleanly from a single drop-in without repeating the directive per server block.

3.3 Validate before reloading

Never reload without testing the syntax. A broken configuration on a remote host is a site visit.

sudo nginx -t && echo "config OK"
sudo nginx -T 2>/dev/null | grep 'ssl_conf_command Groups'

Confirm the second command returns exactly the list intended.

3.4 Reload safely

Roll out to a canary first

Deploy to a single host or a staging environment before the full fleet. Watch handshake error rates and TLS failures in the load balancer or access log for 24 to 48 hours before promoting further.

A reload is graceful. Existing connections drain on the old worker processes while new connections pick up the new configuration.

sudo systemctl reload nginx

Confirm the service is healthy and listening.

systemctl status nginx --no-pager
sudo ss -tlnp | grep :443

04Certificate and signature strategy

Key exchange and server authentication are separate operations in a TLS 1.3 handshake, and they move on different timelines. Pinning the group list in Section 3 addresses key exchange. Authentication is still classical, and staying classical there is the right choice for anything public today.

Keep the certificate on ECDSA or RSA for now. No public certificate authority issues ML-DSA certificates, and no mainstream browser validates them. The certificate algorithm and the key exchange group are independent, so an ECDSA P-256 certificate with X25519MLKEM768 key exchange is a complete and correct configuration. It closes the harvest-now-decrypt-later exposure, which is the time-critical half of the migration.

4.1 Lab exercise: ML-DSA on an internal host

Internal use only

Use a test host or an internal PKI. Do not put an ML-DSA certificate on a public listener.

Generate a self-signed ML-DSA-65 certificate:

sudo openssl req -x509 -newkey mldsa65 \
  -keyout /etc/nginx/pqc/pqc-mldsa.key -out /etc/nginx/pqc/pqc-mldsa.crt \
  -noenc -days 30 -subj "/CN=pqc.test" \
  -addext "subjectAltName=DNS:pqc.test,DNS:localhost,IP:127.0.0.1"

nginx supports multiple certificates in one server block. OpenSSL selects the certificate based on the signature algorithms the client advertises, so PQC-aware clients receive ML-DSA and everything else falls back to ECDSA:

ssl_certificate     /etc/nginx/pqc/pqc-mldsa.crt;
ssl_certificate_key /etc/nginx/pqc/pqc-mldsa.key;

ssl_certificate     /etc/nginx/pqc/pqc-ecdsa.crt;
ssl_certificate_key /etc/nginx/pqc/pqc-ecdsa.key;

Verify with an explicit signature algorithm request:

openssl s_client -connect 127.0.0.1:8443 -servername pqc.test \
  -sigalgs mldsa65 -tls1_3 /dev/null \
  | grep -E 'Peer signature type|Negotiated TLS1.3 group'
Peer signature type: mldsa65
Negotiated TLS1.3 group: X25519MLKEM768

That is a fully quantum-safe TLS 1.3 handshake, using only the OpenSSL default provider. Treat it as the rehearsal for the day public CAs and browsers catch up, not as something to schedule yet.

05Testing

Six tests in increasing order of rigour. Run at least tests 1, 2 and 3.

Test 1: Negotiated group

The single most important check.

openssl s_client -connect host:443 -groups X25519MLKEM768 \
  -tls1_3 /dev/null | grep -E 'Negotiated TLS1.3 group|Protocol|Cipher'

Expected:

Negotiated TLS1.3 group: X25519MLKEM768
Protocol  : TLSv1.3
Cipher    : TLS_AES_256_GCM_SHA384

Any classical curve in that field means the connection is not quantum-safe.

Test 2: The server's advertised groups

Shows what the server offers, independent of what the client requested.

openssl s_client -connect host:443 -tls1_3 -tlsextdebug \
  &1 | grep -A3 supported_groups

Test 3: Negative test

A positive test alone is weak evidence. It proves the preferred path works, not that the pin is actually loaded. Force a classical-only group and confirm the fallback still succeeds under a preferred posture, or is refused under a strict one.

openssl s_client -connect host:443 -groups X25519 -tls1_3 \
  /dev/null | grep 'Negotiated TLS1.3 group'

Under the preferred posture, expect Negotiated TLS1.3 group: X25519. This is the test that catches a drop-in file written but never loaded, since a missing pin and a working fallback look identical from Test 1 alone.

Test 4: HelloRetryRequest check

An HRR costs a full extra round trip. It happens when the client's key shares and the server's group preference disagree.

openssl s_client -connect host:443 -groups X25519MLKEM768:X25519 \
  -tls1_3 -msg &1 | grep -i 'hello retry'

No output is the correct result with a modern client.

Test 5: External scan

sudo apt install -y nmap
nmap -p 443 --script ssl-enum-ciphers host

testssl.sh version 3.2 and later includes explicit PQC group testing and produces a more opinionated report, useful for an evidence pack.

./testssl.sh --curves host:443

Test 6: Measure the cost

Bring numbers when someone asks about performance impact.

for g in X25519 X25519MLKEM768; do
  printf '%-20s ' "$g"
  ( time ( for i in $(seq 1 20); do
      openssl s_client -connect host:443 -groups "$g" -tls1_3 /dev/null 2>&1
    done ) ) 2>&1 | grep real
done

The hybrid handshake carries roughly 1.1 KB more data each way and adds a few milliseconds. On any real network this sits below the round-trip noise floor.

Sequencing note

This test needs the classical group still available for comparison. Run it before applying any strict posture, or against a staging host.

06Compatibility checklist

Test each of these against a candidate server before pinning anything close to strict. This is where rollouts fail.

  • Older browsers and embedded WebViews without hybrid PQC support
  • Health-check and uptime-monitoring clients (curl, wget or Python builds against an older OpenSSL)
  • API clients and SDKs statically linked against an older TLS library
  • CDNs, WAFs and load balancers sitting in front of nginx that terminate or re-originate TLS themselves
  • Upstream reverse proxies or service mesh sidecars proxying to this host
  • IoT and embedded HTTP clients with fixed cipher suite lists
  • Internal scanning, vulnerability management and compliance tooling
  • Any hardcoded ssl_ecdh_curve or ssl_ciphers line in an included server block that could override the drop-in

For anything that fails, upgrade its TLS stack. If that is not possible, keep the preferred posture rather than narrowing to strict, since the classical fallback already covers this case without a special exception.

This differs from the SSH posture

An SSH estate can carve a Match block exception for a specific address range. A public TLS listener cannot identify a visitor before the handshake completes, so there is no equivalent per-client exception. The fallback group list is the only mechanism, which is why the strict posture stays confined to closed environments.

07Evidence to record

Capture the following per host for an audit or assurance file.

  1. nginx -V output, showing the OpenSSL build and run-time versions
  2. nginx -T | grep ssl_conf_command output, showing the effective configuration
  3. Test 1 output, showing the negotiated group
  4. Test 3 output, showing the classical fallback behaves as intended for the chosen posture
  5. Date of the check and the name of the person who ran it
Why items 3 and 4 matter

Together they distinguish a verified control from a configured one. Configuration evidence alone proves intent, not effect.

08What this does not cover

  • Server authentication remains classical. ML-DSA certificates are not viable on a public listener until root store and browser support lands. Section 4.1 is the rehearsal, not the rollout.
  • Certificate chains are unchanged. Intermediate and root certificates in a standard chain still carry classical signatures.
  • Other services need separate assessment. SSH, IPsec, VPN concentrators and application-layer cryptography each have their own migration path. See the companion guide for OpenSSH on this same release.
  • The 26.04 default helps only where both ends are current. A visitor on an old browser or an old client library still negotiates classical key exchange, and that session is not protected. Client-side coverage is the harder half of the problem, and the access-log group breakdown in Section 6 of the companion NGINX build note is the cheapest way to start measuring it.
